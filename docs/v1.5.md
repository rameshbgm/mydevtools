# v1.5 — Cross-tool pipelines, shareable URLs, PWA, browser extension

v1.5 stops adding tools and starts **connecting** them. Four shipping foundations:

1. **Cross-tool pipelines** — any tool's output can be sent into any tool that accepts the same payload kind.
2. **Shareable URLs** — every tool can hand a recipient a URL that restores its input on the other side.
3. **PWA polish** — the long-missing `/manifest.webmanifest` now exists; install button is wired in the footer.
4. **Browser extension** — MV3 right-click launcher; reuses the share-URL format.

## Cross-tool pipelines

### The contract

```ts
// src/lib/tool-bridge.ts
export type ToolPayloadKind = "text" | "json" | "xml" | "csv" | "base64" | "url" | "html" | "binary";

export interface ToolPayload {
    kind: ToolPayloadKind;
    data: string;          // payload (string-encoded; base64 for binary)
    sourceToolId?: string; // for the receiver's banner
    label?: string;        // optional one-liner
    createdAt: number;     // epoch ms — discarded if > 60s old
}
```

Payloads sit in `sessionStorage` for up to 60 seconds, so they survive client-side navigation to the target tool but expire quickly. The target tool reads via `consumeFromBridge()` (one-shot) and either auto-applies or shows a banner.

### Adopting a tool

A typical wiring is ~10 lines:

```tsx
import SendToButton from "@/components/SendToButton";
import ShareButton from "@/components/ShareButton";
import ToolBridgeBanner from "@/components/ToolBridgeBanner";
import { useShareableState, type ShareSchema } from "@/lib/shareable-state";

interface ShareState { input: string; }
const SHARE_SCHEMA: ShareSchema<ShareState> = { toolId: "<your-tool-id>", version: 1 };

export default function YourToolPage() {
    const [input, setInput] = useState("");

    useShareableState(SHARE_SCHEMA, (s) => setInput(s.input));

    return (
        <ToolPageLayout {...}>
            <ToolBridgeBanner accepts={["text"]} onAccept={(p) => setInput(p.data)} />
            {/* existing UI */}
            <ShareButton schema={SHARE_SCHEMA} getState={() => ({ input })} />
            <SendToButton data={output} kind="text" sourceToolId="<your-tool-id>" />
        </ToolPageLayout>
    );
}
```

### Routing — where can my output go?

`BRIDGE_TARGETS` in `tool-bridge.ts` is the source of truth. Each target declares which `ToolPayloadKind`s it accepts. The `SendToButton` filters the menu by the kind you pass it. Add a new target by appending a row to that array — no per-tool changes.

### Tools wired in v1.5

| Tool | Accepts | Emits |
|---|---|---|
| JSON Formatter | `json`, `text` | `json` |
| Base64 | `text`, `base64` | `base64` (encoded) or `text` (decoded) |
| URL Encoder | `text`, `url` | `url` or `text` |
| Hash Generator | `text` | `text` (just forwards input) |
| JWT Decoder | `text` | `json` (the decoded payload) |

## Shareable URLs

### The format

```
https://mydevtools.com/<category>/<tool-id>#s=<base64url(deflate-raw(JSON.stringify({t,v,s})))>
```

- `t` — `toolId`, used to verify the link is for this tool
- `v` — schema version, mismatch → link ignored
- `s` — state object (whatever `getState()` returns)

The state lives in the **URL fragment** (after `#`). Browser fragments are *never sent to a server*, so even on the public site no payload reaches the mydevtools origin. The sender and recipient are the only parties that ever see the data.

### Limits

- 16 KB pre-compression, 12 KB after — well under browser URL limits.
- Returns `null` from `buildShareUrl` instead of silently truncating if the state is too large.

### Sensitive-field warning

`ShareButton` accepts a `sensitiveFieldHint` prop. The JWT Decoder uses this:

> JWT tokens often carry sensitive claims (user IDs, scopes). Only share with people you trust.

## PWA polish

### What was broken

`src/app/layout.tsx` referenced `/manifest.webmanifest` since at least v1.2 but **the file didn't exist** — browsers were silently 404'ing it, breaking installability prompts in Chromium browsers.

### What was added

- `public/manifest.webmanifest` — full metadata, 7 icon entries (16/32/48/180/192/512 + maskable + SVG), 4 launch shortcuts.
- `src/components/PwaInstallButton.tsx` — surfaces the `beforeinstallprompt` event when the browser fires it; auto-hides in `display-mode: standalone`.
- Install button rendered in `AppFooter.tsx` next to the version line. Invisible until installable.

### What was already fine

`public/sw.js` (network-first navigation + runtime cache) and `src/components/PwaRegister.tsx` (registers SW in production builds only) were already in place. No changes.

## Browser extension

Lives under `extension/`. Manifest V3, plain JS (no bundler), readable end-to-end.

### Files

```
extension/
├── manifest.json    # MV3 manifest
├── background.js    # service worker: context menus + share-URL builder
├── popup.html       # toolbar popup
├── popup.js
├── options.html     # site-origin config (for self-hosters)
├── options.js
├── icons/           # PNGs to be supplied before publishing
└── README.md
```

### How the handoff works

The extension's `background.js` contains a copy of the share-URL builder (deflate-raw + base64url) — about 30 lines. When the user right-clicks → picks a tool, it:

1. Reads `info.selectionText`
2. Wraps it as `{ t: toolId, v: 1, s: { input: text, ...extras } }`
3. Encodes to base64url-deflate-raw and appends as `#s=...`
4. Opens `chrome.tabs.create(url, …)`

The target tool's `useShareableState` hook reads the fragment on mount and pre-loads the input.

**Why duplicate the encoder in the extension?** Two reasons: (1) no build step, so the extension can't `import` from the Next.js source; (2) keeping the format documented in two places forces version-bump discipline.

### Privacy posture

- **No `host_permissions`** — the extension can't read page content; it only sees what you explicitly select.
- **No telemetry** — codebase contains no analytics, no remote pings.
- **Self-host friendly** — point the extension at any origin via the popup or options page.

## What's next

The foundation is the win — adopting it across all 104 tools is a long tail of ~10-line PRs. Prioritise the most-used tools:

1. All formatters (XML, YAML, SQL, HTML, JS, CSS) — they all accept and emit `text`
2. All validators — accept output from formatters
3. All converters — chain JSON → CSV → JSON-to-TypeScript naturally
4. The diff tools — accept output from formatters as the left input

Each one is the same 5-import + 3-component-drop pattern as the flagships.
